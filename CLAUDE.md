# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project state

Qt6/C++ LAN file-transfer client-server application, product name **LanDrop** (repo is hosted on GitHub as `LanDrop`; on the primary dev machine the local checkout happens to sit inside an identically-named `FTP_Soft` wrapper folder — a local artifact, not present in a fresh clone). QSettings organization/application name is `LanDrop`/`LanDrop_Server`/`LanDrop_Client` (changed from the old `FTP_Soft`/`FTP_Soft_Server`/`FTP_Soft_Client` — any settings saved under the old names, e.g. from earlier manual testing, will not carry over).

**Architectural migration to standard FTP (RFC 959) is complete.** The project was rewritten from a Qt-based custom binary protocol (`QTcpSocket`, `QDataStream` framing, `QThread`/`QTimer`) to a strict split: a Qt-free `core/` (native OS sockets, `std::thread`/`std::mutex`/`std::condition_variable`/`std::atomic`, real **RFC 959 FTP** — connects to arbitrary third-party FTP servers, not just two devices both running LanDrop) with Qt used *only* in the GUI layer (`client/`, `server/`), bridged via `std::function` callbacks (`core/callbacks.h`, `core/ftp/ftp_transfer_manager.h`, `core/discovery/lan_discovery.h`) that thin Qt wrappers turn into signals via `QMetaObject::invokeMethod(..., Qt::QueuedConnection)`. The old custom-protocol classes (`common/protocol.*`, `server/session.*`, `server/datachannelserver.*`, `server/filemanager.*`) have been **deleted** — `client/connection.*`, `client/transfer.*`, `server/ftpserver.*` were rewritten in place (same class names/public signatures, internals now delegate to `core::`). LAN auto-discovery (custom UDP broadcast, not mDNS) is implemented. SFTP client support was considered and explicitly declined (see git history) — not planned.

Cross-platform release packaging **is** implemented: `.github/workflows/release.yml` builds macOS/Windows/Linux on every `v*.*.*` tag push (or manually via `workflow_dispatch`) and, on a tag push, creates a GitHub Release with the packaged artifacts attached.

The migration landed in phases (each independently compiled/verified, not written blind in one pass — see git history for the individual commits):
- **Phase A.** `core/platform/socket.{h,cpp}` (native TCP socket RAII wrapper), `core/platform/udp_socket.{h,cpp}` (UDP counterpart, used by discovery), `core/heartbeat.{h,cpp}` (protocol-agnostic interruptible heartbeat thread), `core/hash/sha256.{h,cpp}` (self-contained, no external dep), `core/callbacks.h`. `ftpcore` CMake static-lib target — verify it stays Qt-free with `otool -L build/socket_smoke_test` (or equivalent) whenever you touch it; `AUTOMOC`/`AUTORCC`/`AUTOUIC` are explicitly turned off on `ftpcore` and all `core/tests/*` targets even though they're project-wide `ON` for the Qt targets. SHA-256 test vectors were generated with `shasum -a 256`, not typed from memory (verify any new ones the same way).
- **Phase B.** `core/ftp/ftp_client.h/.cpp`: `FtpClient`, a real RFC 959 FTP client state machine (`USER`/`PASS`/`TYPE I`/`PWD`/`CWD`/`MKD`/`RMD`/`DELE`/`RNFR`+`RNTO`/`PASV`/`LIST`/`MLSD`(via `FEAT` probe, falls back to best-effort Unix `ls -l` parsing)/`RETR`/`STOR`/`REST`/`NOOP`/`QUIT`). All public methods are **synchronous/blocking** — the calling side runs them on its own `std::thread` (see Phase D/G). `Socket::sendSome()` (partial-send, mirrors `recvSome()`) exists so uploads can do a cancellable, timeout-bounded chunked send loop instead of `sendAll()`'s internal indefinite wait. **Heartbeat/transfer interaction**: the control-channel NOOP heartbeat is paused for the whole duration of any `downloadFile`/`uploadFile` call — RFC 959's control connection is strict request/response, and an interleaved `NOOP` during `RETR`/`STOR` would garble the reply stream; the heartbeat only covers the idle/browsing window. Chunk size is 256KB (`kChunkSize`). Cancellation (`cancel()`) is a polled `std::atomic<bool>` checked every chunk; on cancel the data socket closes and a best-effort `ABOR` is sent. **`parsePasvReply`/`parseListLine`** are `static` public methods, unit-testable without a live server.
- **Phase C.** `core/ftp/ftp_server.h/.cpp` (`FtpServer`: accept thread + one `std::thread` per client) and `core/ftp/ftp_session.h/.cpp` (`FtpSession`: the per-connection RFC 959 state machine — `USER`/`PASS`/`PWD`/`XPWD`/`CWD`/`XCWD`/`CDUP`/`XCUP`/`TYPE`/`PASV`/`LIST`/`MLSD`/`RETR`/`STOR`/`REST`/`MKD`/`XMKD`/`RMD`/`XRMD`/`DELE`/`RNFR`+`RNTO`/`NOOP`/`FEAT`/`SYST`/`QUIT`). `PASV` allocates an ephemeral port via `bindAndListen(0)` + `Socket::localPort()` and reports it with `Socket::localAddress()` (mirrors `peerAddress()` via `getsockname`, deliberately the interface the client actually connected to). Data listener is one-shot, re-armed by every `PASV`. Auth: `FtpServer::Authenticator` (`std::function<bool(user,pass)>`) — **safe-by-default**, no `Authenticator` set means every login is rejected. Path safety is a separate, independently tested module, `core/ftp/ftp_paths.h/.cpp` (`normalizeFtpPath`/`isValidFtpName`, `std::filesystem`-based) specifically because the old Qt equivalent (`Utils::normalizePath`) had a real bug once (forgot to strip the leading `/`, letting every op fall through to the root) — regression-tested plus `..`-escape and string-prefix-boundary traversal attempts. No per-transfer `ABOR` handling server-side — an accepted simplification (see Phase E note on the resync bug this caused, now fixed client-side).
- **Phase D/E ("阶段 E" in commit history — client concurrency).** `core/ftp/ftp_transfer_manager.h/.cpp`: `FtpTransferManager`, a fixed pool (default 3) of workers, each a persistent logged-in `core::FtpClient` + dedicated `std::thread` pulling from a shared task queue — standard FTP's control connection can only do one thing at a time, so concurrent transfers need independent FTP sessions (same approach FileZilla etc. use), not a token handshake on a shared control channel like the old protocol had. Pause = `FtpClient::cancel()` on the task's current worker; resume = requeue with `REST` at the task's recorded `bytesTransferred`. Failed transfers retry with linear backoff via a dedicated retry thread (`cv.wait_until` to the nearest deadline, not `sleep_for` polling). Core reports every raw progress chunk unthrottled by design — throttling is the Qt adapter's job (see Phase G). **Real bug found and fixed while building this**: `FtpClient`'s cancel path sent `ABOR` and read exactly one reply assuming it was `ABOR`'s — but our own `FtpServer` has no `ABOR` support, so closing the data socket makes the server's `STOR` loop see a clean EOF and reply `226` *before* `ABOR` is even parsed as a command, leaving the real `ABOR` reply (`502`) stuck unread and desyncing every subsequent command on that connection. Fixed by draining the original command's completion reply first, then sending `ABOR` as a lenient best-effort probe. This is why pausing an upload and resuming it on the same connection needs both halves of that fix to work.
- **Phase F (server callbacks + LAN discovery).** `FtpServer`/`FtpSession` gained `TransferStartedCallback`/`TransferProgressCallback`/`TransferCompletedCallback` (bundled into `FtpServer::SessionCallbacks` so the constructor doesn't keep growing positional params), throttled to ~200ms *inside* `FtpSession`'s `RETR`/`STOR` loops (not left to the Qt adapter here, unlike the client side — throttling before the cross-thread `invokeMethod` hop reduces actual event-queue load, not just repaint cost). `STOR` reports `total=0` (RFC 959 has no client-side-declared file size on upload — same convention `FtpClient` already used); `RETR` reports the real size. `core/discovery/lan_discovery.h/.cpp`: custom UDP broadcast (`DiscoveryBeacon`/`DiscoveryListener`, port `kDefaultDiscoveryPort` = 52121, one-line `LANDROP1|name|port` packets) — not mDNS/DNS-SD, since the actual requirement is just "LanDrop finds LanDrop." `DiscoveryListener`'s update callback only fires when the visible device list actually changes (new/removed/renamed), not on every heartbeat rebroadcast.
- **Phase G (GUI wiring).** `client/connection.*`, `client/transfer.*`, `server/ftpserver.*` rewritten in place — same class names/public signatures (`Connection`, `TransferQueue`, `FTPServer`), internals now thin Qt wrappers delegating to `core::`. `Connection` owns one `std::thread` running a serial job queue against a single `core::FtpClient`; results come back via `invokeMethod(..., Qt::QueuedConnection)`. Removed dead/obsolete `Connection` API confirmed to have zero external callers: `requestUpload`/`requestDownload`/`cancelTransfer`/`transferReady`/`dataPort()` (token-handshake artifacts of the old protocol) and `changeDir()`/`directoryChanged` (was dead code even before this change). `TransferQueue` no longer takes a `Connection*` — it owns its own `core::FtpTransferManager`, wired up via a new `setConnectionInfo(host, port, user, pass)` called once after login (see `MainWindow::onLoginResult`). The 200ms client-side progress throttle lives here, gated *before* the `invokeMethod` hop. `FTPServer` no longer extends `QTcpServer` (`core::FtpServer` does its own accept loop on native sockets). `common/ftptypes.h` holds the small pieces still needed post-migration (`FTP::FileInfo`, `FTP::DEFAULT_PORT`) that used to live in `common/protocol.h`. **Known limitation**: `core::FtpClient::parseListLine` doesn't extract MLSD's `Modify` fact or `LIST`'s timestamp/permission text, so the remote browser's "修改时间"/"权限" columns are blank when connected via the new core (local browsing unaffected) — documented in `ftptypes.h`, not silently dropped.

**Known regression from moving to standard FTP** (surfaced to the user, not an oversight): RFC 959 has no built-in post-transfer integrity check the way the old custom protocol did. Against third-party FTP servers there's no portable fix. Against our own `core/ftp/ftp_server`, a non-standard extension gated behind `FEAT` capability discovery is a possible future addition, not currently implemented.

Requirements doc: `需求书.md` (repo root, same directory as this file). Read it before making non-trivial changes.

## Working agreement

- **Explain before touching connection management, the session state machine, or anything architectural** — describe the approach and blast radius, wait for confirmation, then implement. Routine feature work (a single new command, a test, docs) doesn't need this.
- **Small, independently verifiable steps.** One problem per change; don't fold in unrelated cleanup.
- **Don't expand scope unasked.** Prefer a narrow fix that's stable over a larger one that "also handles" adjacent cases.
- **When RFC 959 is ambiguous or underspecified for a given case, present the options and tradeoffs and let the user pick** — don't unilaterally commit to a complex interpretation.
- **Model routing**: architecture/state-machine design and hard concurrency/timing bugs (connection leaks, race conditions) → Opus. Routine command implementation, tests, docs → Sonnet (default). Mechanical renames/formatting → Haiku.

Design invariants to preserve when touching the FTP engine (already reflected in the Phase A–G work above, but worth restating as a checklist for future changes): control connection (long-lived, request/response) and data connection (per-transfer, opened and closed around a single `LIST`/`RETR`/`STOR`) must stay independently managed with their own error/cleanup paths; session state (unauthenticated → authenticated → transferring → idle → closed) should gate which commands are legal in one place (`FtpSession`'s state, not scattered `if`s); reply codes must stay strict RFC 959 three-digit codes (227 for `PASV`, 150/226 for transfers, 331/230 for auth, etc.); every socket/file handle needs a traceable close path, including on exception/error branches — this class of bug (resource leaks) has been the highest-frequency bug category in this codebase.

## Architecture

### Targets (`CMakeLists.txt`)
- `common` — static library shared by both client and server (`common/utils.cpp` — password hashing, file hashing, human-readable formatting; protocol-agnostic).
- `ftpcore` — Qt-free static library, the `core/` FTP engine (see below).
- `landrop_server` — server GUI executable (`server/`), links `common` + `ftpcore`.
- `landrop_client` — client GUI executable (`client/`), links `common` + `ftpcore`.

### Core (`core/`) — Qt-free, native sockets, standard FTP (RFC 959)
- `core/platform/socket.h/.cpp`, `udp_socket.h/.cpp` — RAII TCP/UDP socket wrappers, `#ifdef _WIN32` winsock2 vs BSD socket.
- `core/platform/path_utf8.h/.cpp` (`utf8ToPath`/`pathToUtf8`) — safe UTF-8 ↔ `std::filesystem::path` conversion. Every filename/path that crosses the protocol boundary (FTP wire text) must go through these instead of `fs::path(std::string)`/`path::string()` directly — on Windows those default to the process's ANSI codepage, not UTF-8, and throw on filenames outside it (see Known issues below for the real bug this caused). No-op passthrough on POSIX, where narrow encoding already is UTF-8.
- `core/heartbeat.h/.cpp` — protocol-agnostic interruptible-wait heartbeat thread.
- `core/hash/sha256.h/.cpp` — self-contained SHA-256 (no `QCryptographicHash` dependency at this layer).
- `core/ftp/ftp_client.h/.cpp` (`FtpClient`) — synchronous/blocking RFC 959 client state machine; see phase history above for the full command list and design notes.
- `core/ftp/ftp_server.h/.cpp` + `ftp_session.h/.cpp` (`FtpServer`/`FtpSession`) — accept-thread + thread-per-client RFC 959 server.
- `core/ftp/ftp_paths.h/.cpp` — path safety (`normalizeFtpPath`/`isValidFtpName`), independently tested.
- `core/ftp/ftp_transfer_manager.h/.cpp` (`FtpTransferManager`) — client-side concurrent transfer pool (see Phase D/E above).
- `core/discovery/lan_discovery.h/.cpp` (`DiscoveryBeacon`/`DiscoveryListener`) — LAN auto-discovery.
- `core/callbacks.h` — shared `std::function` callback typedefs.

Verify `ftpcore` stays Qt-free after any change: `otool -L build/socket_smoke_test` (or any other `core/tests/*` binary) should show only `libc++`/`libSystem` (macOS) — nothing from `Qt*.framework`.

### Server (`server/`)
- `FTPServer` (`ftpserver.h/.cpp`) — thin `QObject` wrapper over `core::FtpServer` (does **not** extend `QTcpServer` — the core does its own accept loop on native sockets). Bridges `core::FtpServer`'s `std::function` callbacks (log messages, per-session transfer started/progress/completed, both structured *and* text) into Qt signals via `QMetaObject::invokeMethod(..., Qt::QueuedConnection)`. Passwords are salted-hashed (`Utils::hashPassword`/`verifyPassword`) — never stored or compared in plaintext, kept in an in-memory `QMap` guarded by `std::mutex` (the `core::FtpServer::Authenticator` callback fires from arbitrary session background threads, concurrently with the UI thread calling `addUser()`/`removeUser()` — this needs real thread-safety, not just Qt's usual single-threaded-by-convention assumption). `userHashes()`/`addUserWithHash()` exist so `ServerWindow` can persist/restore already-hashed credentials via `QSettings` without ever touching plaintext. `setDiscoveryEnabled()`/`isDiscoveryEnabled()` wrap a `core::DiscoveryBeacon`.
- `ServerWindow` (`serverwindow.h/.cpp`) — "允许被局域网自动发现" checkbox (persisted via `QSettings`, starts/stops the beacon; also re-armed automatically on service restart if it was checked).

### Client (`client/`)
- `Connection` (`connection.h/.cpp`) — thin `QObject` wrapper over `core::FtpClient`. Owns one `std::thread` running a serial job queue (`std::mutex`+`std::condition_variable`, interruptible wait) against a single, thread-private `core::FtpClient` instance; every public method (`login`, `listDirectory`, `mkdir`, `rmdir`, `deleteFile`, `rename`) pushes a job whose result comes back as a Qt signal via `QMetaObject::invokeMethod(..., Qt::QueuedConnection)`. `isConnected()` reads a plain `std::atomic<bool>` so it stays a cheap synchronous call from the UI thread without touching the `FtpClient` itself (which only the worker thread ever touches). `disconnectFromHost()` synchronously joins the worker thread — bounded by `FtpClient`'s own internal timeouts, same tradeoff `FtpServer::stop()`/`FtpTransferManager::stop()` already make elsewhere in this codebase.
- `TransferQueue` (`transfer.h/.cpp`, `QAbstractTableModel`) — thin Qt wrapper over `core::FtpTransferManager` (constructed via `setConnectionInfo(host, port, user, pass)`, called once from `MainWindow::onLoginResult()` — **not** in the constructor, since credentials aren't known until login succeeds). Standard FTP's control connection can only do one thing at a time, so — unlike the old protocol, which could request a transfer token over a shared control channel — concurrent transfers each need their own independent FTP session; `FtpTransferManager` owns a small pool of those (default 3, matches the old `m_maxConcurrent`). `pauseRow()`/`resumeRow()`/`cancelRow()` delegate straight through to the manager (`FtpClient::cancel()` under the hood + `REST`-based resume from the task's last known `bytesTransferred`).
  - **Progress throttling**: `FtpTransferManager` reports every raw progress chunk unthrottled by design (core stays policy-free) — `TransferQueue` throttles to ~200ms *before* the cross-thread `QMetaObject::invokeMethod` hop (a `std::mutex`-guarded `std::map<QString, qint64>` of last-report timestamps per task id, since multiple tasks can report concurrently from different worker threads). This mirrors the original bug fix (see below) but gates earlier — before the thread-crossing dispatch, not just before the repaint — since an unthrottled callback would otherwise flood the Qt event queue itself, not merely cost more repaints.
- `FileBrowserPanel` (`filebrowser.h/.cpp`) — same widget/model (`FileEntryModel`) drives both the local (`QDir`-backed) and remote (`Connection`-backed) panes; only the data source differs. Remote pane's "修改时间"/"权限" columns are blank when connected via the new core (`core::FtpClient` doesn't parse MLSD's `Modify` fact or `LIST` timestamp/permission text yet — known limitation, not a bug). Selecting a folder for "上传到远程当前目录"/"下载到本地当前目录" emits `folderUploadRequested`/`folderDownloadRequested` (separate from `uploadRequested`/`downloadRequested`, which only ever carry files) — `MainWindow` forwards these to `FolderTransferCoordinator`.
- `FolderTransferCoordinator` (`foldertransfer.h/.cpp`) — standard FTP has no "transfer this whole directory" command, so folder upload/download is client-side orchestration on top of the existing primitives: upload walks the local tree with `QDirIterator` (depth-first, so a directory is always yielded before its own children — gives the "parent before child" order for free), issues one `Connection::mkdir()` per remote directory level (not a single recursive call — most third-party FTP servers' `MKD` only creates one level, unlike our own server's `fs::create_directories`), waits for *all* of them to come back (success or "already exists" failure, doesn't matter which) before enqueueing any file via `TransferQueue::enqueueUpload()` — otherwise a `STOR` could race ahead of its parent directory's `MKD`. Download is a breadth-first walk over `Connection::listDirectory()`/`directoryListed`, matched by the echoed-back `path` (`Connection::listDirectory()`/`mkdir()` always use absolute virtual paths, so this doesn't get confused by `FileBrowserPanel`'s own independent, user-driven browsing calls interleaving on the same signals), creating local directories synchronously via `QDir::mkpath()` and enqueueing files via `TransferQueue::enqueueDownload()`. Deliberately not a `QWidget` — same "core logic separated from Qt wiring, independently testable" approach as `TransferQueue`/`Connection` — so it's covered directly in `tests/gui_core_integration_test.cpp` against a real `FtpServer`, not just manual GUI clicking. **Known limitation**: only one folder-transfer batch is tracked in flight per direction at a time, because `Connection::operationResult` doesn't echo back which `mkdir()` call it belongs to — if the user manually triggers an unrelated remote operation (delete/rename/mkdir from the context menu) while a folder upload's directory-creation phase is in flight, its `operationResult` could be miscounted and files enqueued a little early. Accepted simplification, not an oversight.
- `SiteManagerDialog` (`sitemanager.h/.cpp`) — saved connection profiles in `QSettings`, plus a "局域网发现" panel (`core::DiscoveryListener` runs for the dialog's lifetime; double-click a discovered device to fill host/port into the form). "Remember password" stores it in plaintext in the local settings file (documented in the UI copy) — acceptable for personal-LAN use, not a general credential store.

### Utils (`common/utils.h/.cpp`)
- `hashPassword`/`verifyPassword` — salted SHA-256, format `"saltHex:hashHex"`.
- `fileHash` — SHA-256 over a file's full contents (not currently wired into the new FTP core's transfer path — RFC 959 has no built-in post-transfer integrity check, see the known-regression note above; kept around as a general utility and used by the older commit history's verification tooling).
- `formatFileSize`/`formatSpeed`/`formatDuration` — human-readable formatting; `formatDuration` returns Chinese unit labels (秒/分/时).

## Verification

**`core/` logic**: each of the 7 Qt-free `core/tests/*` binaries drives real sockets/servers/clients over real loopback TCP/UDP — no mocks. Run all of them after touching anything under `core/`.

**GUI-core wiring (`client/connection.*`, `client/transfer.*`, `server/ftpserver.*`)**: `tests/gui_core_integration_test.cpp` is a headless Qt console program (no `QWidget` dependency) that links `common/utils.cpp`, `client/connection.cpp`, `client/transfer.cpp`, `server/ftpserver.cpp` directly and drives a real `FTPServer` + `Connection` + `TransferQueue` against each other over `127.0.0.1` in one process — continuing this project's established methodology of writing a small headless Qt console harness rather than relying on GUI automation alone. Covers connect/login/list/mkdir, upload+download with byte-for-byte SHA-256 verification through the real `TransferQueue` model, pause/resume/cancel through `TransferQueue::pauseRow()`/`resumeRow()`/`cancelRow()` (not just the underlying `FtpTransferManager`, which Phase E already covers directly), and folder upload/download through `FolderTransferCoordinator` (nested subdirectories, byte-for-byte content verified both directions against a real `FtpServer`). The pause/resume case is deterministic in practice: it polls for `BytesTransferredRole > 0` before calling `pauseRow()`, which reliably lands mid-transfer for a 100MB file without needing a callback-injection hook. A one-off manual run with the pause-test file bumped to 1.5GB confirmed the whole thing (including a full resumed transfer) completes cleanly in ~34s on loopback with no disconnects — re-validating the original large-file bug class (below) doesn't reproduce on the new stack; that large-file variant isn't kept in the committed version (100MB is enough to exercise the same code paths and keeps the suite fast).

**GUI click-through**: on macOS this is scriptable via `osascript`/System Events (`tell application "System Events" to tell process "landrop_client" to click button "连接" of window 1`, etc.) — but the process needs Accessibility permission granted to whatever app runs the shell (check with `ps -p $$ -o ppid=` walked up to the terminal app, e.g. Terminal.app, then grant it under System Settings → Privacy & Security → Accessibility). Use `entire contents of window 1` to dump the accessibility tree and find exact element names before scripting clicks.

- **Known Qt/macOS crash trigger**: any UI automation interaction (typed keystroke, or apparently also plain button clicks/queries in some cases) landing at the same moment a `QAbstractItemModel::beginResetModel()/endResetModel()` fires (e.g. `FileBrowserPanel`'s `refresh()` → `FileEntryModel::setEntries()`, or the remote pane's auto-navigate-to-root right after a successful login) can crash the whole app with `SIGSEGV` inside Qt's Cocoa accessibility bridge (crash frame `libqcocoa.dylib`, called from `CoreFoundation`/`HIToolbox`/`AppKit` — confirmed via `~/Library/Logs/DiagnosticReports/*.ips`, same crashing frame offset across multiple independent repro attempts) — this is a Qt 6.8 framework bug triggered by accessibility tooling actively walking the UI tree during a model reset, not application-level UB. Reproduced multiple times during the Phase G/H GUI verification pass alone. When this class of crash makes continued UI-scripted testing impractical, fall back to the headless Qt integration test above instead of continuing to fight it — it exercises the identical production code (not a mock) and won't hit this Qt/AppKit-specific issue at all.
- Two real, non-cosmetic bugs were only found through actually clicking through the GUI (not caught by the headless harness or code review, back in the original custom-protocol implementation): (1) the "connect" action was originally only reachable via the macOS global menu bar, invisible inside the app window itself — always give primary actions a visible in-window toolbar button, not just a menu item; (2) `MainWindow::onOpenSiteManager()` treated "remember password" (a *persistence* flag) as a proxy for "was a password entered" — it discarded the password the user had just typed in the Site Manager dialog and re-prompted for it via a redundant popup whenever "记住密码" was left unchecked. Fixed by only prompting when the password field is actually empty.

**Interop and leak checks** (in addition to the 8 committed test binaries above): when adding/changing a command, cross-test against a real third-party FTP client/server (`ftp`, `lftp`, FileZilla, `curl ftp://`), not just our own client against our own server. After repeated `RETR`/`STOR` cycles, check for socket/file-handle leaks with `lsof`/`netstat` — this has historically been the highest-frequency bug category in this codebase (see Phase D/E's `ABOR` desync bug above). Verify large-file transfers with an md5/sha256 comparison against the source file.

## Known issues (reported, not yet root-caused)

- ~~**Windows server + non-ASCII filename → mid-transfer disconnect.**~~ **Fixed.** Root cause confirmed by reading (message matched exactly, no live Windows repro needed): `core/ftp/ftp_session.cpp` (and `core/ftp/ftp_paths.cpp`) constructed/read `std::filesystem::path` via the plain narrow-string constructor and `.string()` accessor at every filename touch point (`handleList`/`handleRetr`/`handleStor`/`handleMkd`/`handleRnto`'s filename checks, `normalizeFtpPath`). On Windows, `fs::path` stores UTF-16 internally and its narrow conversions default to the process's **ANSI codepage**, not UTF-8 (macOS/Linux are unaffected because their narrow encoding already *is* UTF-8). A filename with characters outside that codepage makes `.filename().string()` throw `std::system_error` with exactly the reported text — this is the documented MSVC STL message for this exact failure mode. The exception propagates to `FtpSession::run()`'s top-level `catch (const std::exception& e)` (`log("session terminated by unexpected exception: " + e.what())`); only that one session dies, not the whole server (the process-wide-crash class of bug this catch guards against is a separate, already-fixed concern — see `ftp_paths.cpp`'s `safeWeaklyCanonical` comment).
  - Fix applied: new `core/platform/path_utf8.h/.cpp` (`utf8ToPath`/`pathToUtf8`) — on Windows these explicitly convert UTF-8 ↔ UTF-16 via `MultiByteToWideChar`/`WideCharToMultiByte(CP_UTF8, ...)` instead of relying on the ANSI-codepage-assuming default conversions; on POSIX they're a zero-overhead passthrough. Every `fs::path`/`.string()` touch point in `ftp_paths.cpp` and `ftp_session.cpp` now goes through these, and the same fix was applied to the client side's local-file I/O in `core/ftp/ftp_client.cpp` (`uploadFile`/`downloadFile`'s `ifstream`/`fstream` opens) since it had the identical bug in reverse (a LanDrop client running on Windows with a non-ASCII local file path). Verified: all 8 `core/tests/*` binaries + `tests/gui_core_integration_test` pass; `ftpcore` confirmed still Qt-free; added a regression block to `core/tests/ftp_server_test.cpp` that uploads/lists/downloads/renames/deletes a file with a Chinese+emoji name end-to-end (can't reproduce the Windows-specific codepage exception on macOS/Linux, but locks in that the refactor itself didn't regress non-ASCII filename handling on the platforms this project develops on day-to-day).
- ~~**Progress column and completion state break after a client reconnect.**~~ **Fixed.** Root cause confirmed by reading, not guessed: `MainWindow` keeps a single long-lived `TransferQueue` for the app's lifetime and calls `setConnectionInfo()` on every successful login, including reconnects (`mainwindow.cpp` `onLoginResult`). `setConnectionInfo()` (`client/transfer.cpp`) `stop()`s the old `core::FtpTransferManager` and `new`s a fresh one, but never clears `TransferQueue::m_tasks` — completed rows from the prior session stay in the model. `FtpTransferManager::nextTaskId()` (`core/ftp/ftp_transfer_manager.cpp`) drew from an atomic counter that was a *per-instance* member, so the new manager restarted numbering at `"task-1"` — colliding with whatever id the first row of the previous session already had. `TransferQueue::rowForId()` returns the *first* matching row, so post-reconnect progress/state callbacks silently updated the old, already-completed row instead of the newly appended one, leaving the real new row stuck on "排队中" with no progress forever.
  - Fix applied: `m_taskCounter` is now a process-wide `static std::atomic<uint64_t>` (`FtpTransferManager::s_taskCounter`) shared across every instance, so ids stay unique across reconnects/manager rebuilds no matter how many times `setConnectionInfo()` runs. Verified: all 8 `core/tests/*` binaries plus `tests/gui_core_integration_test` still pass; `ftpcore` confirmed still Qt-free via `otool -L`. Not yet covered by a committed regression test for the specific "second `FtpTransferManager` instance in the same process" scenario — worth adding if this class of bug recurs.
- ~~**Progress bar renders in the wrong column / doesn't render at all for rows after the first.**~~ **Fixed on the third attempt.** Two prior commits (`546e985`, `eb28882`) both tried to fix this exact user-reported symptom by tweaking `QStyleOptionProgressBar` field initialization inside a hand-rolled `QStyledItemDelegate::paint()` (`client/transferwidget.cpp`) — both shipped, both confirmed-failed by fresh user screenshots afterward (the second fix's own commit message hedged "can't fully confirm... without the user testing a new build", and that hedge turned out to matter). Rather than guess a third variant of the same delegate's style-option fields, replaced the whole rendering approach: `TransferProgressDelegate` is gone; each row's "进度" cell now hosts a real `QProgressBar` via `QTableView::setIndexWidget()`, updated from `TransferQueue::dataChanged`/`rowsInserted` (see `TransferWidget::updateProgressCell()`). Qt's own widget geometry management positions and repaints it — no more hand-derived `QStyleOptionProgressBar::state`/`rect`. Verified visually (not just "should work"): a throwaway harness driving a real `FtpServer` + `TransferQueue` + `TransferWidget` through concurrent uploads and grabbing `QWidget::grab()` screenshots showed all rows rendering correctly-positioned progress bars.
- ~~**Progress bar's centered "NN%" text overlaps/becomes illegible on macOS (renders fine on Windows).**~~ **Fixed.** Follow-up to the fix above: putting a real `QProgressBar` in the cell solved the column-position bug, but `setTextVisible(true)`'s centered text overlay still visually collided with `QMacStyle`'s native rounded progress-bar rendering specifically on macOS (Windows' native style has no such conflict — a platform rendering difference, not a logic bug, confirmed by the user's own side-by-side macOS-vs-Windows screenshots). - **Folder upload/download added.** Previously, selecting a folder for "上传到远程当前目录"/"下载到本地当前目录" silently skipped it (`client/filebrowser.cpp` explicitly filtered `if (!entry.isDir)`) — reported because FileZilla could upload folders against the same LanDrop server (server-side already handles nested `STOR`/`MKD` fine; the gap was entirely client-side). - **FTPS (explicit `AUTH TLS`, RFC 4217) is not supported — by decision, not oversight.** Connecting to a real FileZilla Server configured to require TLS fails with `USER rejected: Use AUTH first`, because `core::FtpClient` only speaks plaintext RFC 959 and never sends `AUTH TLS`. This is **not** the same thing as SFTP (a completely different protocol over SSH, already declined — see Project state above); FTPS is TLS wrapped around the same FTP command set LanDrop already implements. Supporting it would require a TLS library — either OpenSSL inside `core/` (keeps `core/` Qt-free, but adds a new external dependency that has to be built/bundled on macOS/Windows/Linux CI) or Qt's `QSslSocket` (much less new code, but would break the `core/`-never-touches-Qt architectural invariant this project has otherwise maintained throughout, verified by the `otool -L` check in every `core/tests/*` run). Explicitly deferred for now — connecting to a TLS-only third-party server is an expected, documented limitation, not a bug to chase.
